Mac and Linux packages

Build each package on its native OS, validate the exact source commit, then package the binary. Packaging does not run tests and does not certify a release.

Platform-specific builds

On Apple-silicon macOS:

cargo build --release --locked --target aarch64-apple-darwin
python3 scripts/package_release.py \
  --binary target/aarch64-apple-darwin/release/target-reaper \
  --target aarch64-apple-darwin --output target/packages

On x86-64 Linux:

cargo build --release --locked --target x86_64-unknown-linux-gnu
python3 scripts/package_release.py \
  --binary target/x86_64-unknown-linux-gnu/release/target-reaper \
  --target x86_64-unknown-linux-gnu --output target/packages

The packager checks the executable's OS/architecture header, records binary and source fingerprints, and creates an archive plus checksum manifest. Its default label is development; use a release label only as part of an actually verified release process.

Package contents

File Purpose
target-reaper Native executable for the named target
BUILD.json Commit, dirty-source state, source fingerprint, binary hash and package target
INSTALL.md Installation and documentation link
SHA256SUMS Checksums for packaged files

The archive also receives a sidecar .sha256 checksum. The packaging_checkout_commit, packaging_checkout_dirty and packaging_checkout_source_sha256 fields describe the checkout used for packaging. They do not by themselves prove which source produced the supplied binary. build_binding defaults to Unverified. Passing --verification-receipt PATH requires matching source, binary, target and passing native-test evidence, records the receipt/test-log hashes, and labels the relationship as local evidence rather than a signed attestation. An older tag or an artifact uploaded by a workflow must not be presented as a verified current-head build without its native test evidence.

Verify before installing

On macOS, use shasum -a 256 ARCHIVE.tar.gz. On Linux, use sha256sum ARCHIVE.tar.gz. Compare the result to the sidecar checksum from the same trusted release.

Inspect BUILD.json after extraction, confirm the target matches your machine, then install for your user:

install -d "$HOME/.local/bin"
install -m 755 target-reaper "$HOME/.local/bin/target-reaper"
"$HOME/.local/bin/target-reaper" --version

Unsigned development Mac binaries are not notarized applications. A binary that runs on the verification Mac is not automatically certified for all older macOS versions.

Distribution boundary

The source repository and its release assets are private. Public documentation does not grant download access. No new production release is claimed until the matching Mac and Linux artifacts and required verification actually exist.

Prepared native build workflow

.github/workflows/native-versions.yml targets macos-15 on ARM64 and ubuntu-24.04 on x86-64. It uses official checksum-pinned native test tools, a read-only token, one build job and two test threads. It produces development archives only after its native checks pass.

Hosted runners are VMs. Where a task forbids VM substitution, obtain explicit approval before using them. The workflow stays gated until a manual dispatch explicitly approves hosted runners, or an authorized same-repository PR receives the native-runners-approved label. A skipped job is not a passing verification result.

Jobs have a 20-minute outer limit; individual monitored stages stop at 1 GiB sampled owned RSS, 2 GiB build cache, a 4 GiB free-space floor, low available memory or the 15-minute stage watchdog. The build-cache limit counts the full owned cache, not a reset baseline between stages. macOS also uses the native write/network sandbox; Linux uses a dedicated disposable runner with isolated fixture HOME/TMPDIR and VCS configuration.

This workflow does not waive vet provenance, dependency policy or other release-assurance obligations. Workflow artifacts are not automatically published as production releases.
